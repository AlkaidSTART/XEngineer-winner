# 七牛云项目横向整合

## 目标

把多个项目从“并排点评”提升为“可比较的系统”：找出哪些能力反复出现、哪些获奖因素可迁移、哪些项目适合生产化、哪些模块可以合并，以及学习顺序如何安排。不要用一个总分掩盖项目类型和成熟度差异。

## 输入与准备

1. 确认分析范围：全部项目、用户点名项目，或按方向筛选的子集。
2. 扫描顶层目录、README、docs、构建配置和部署文件，建立项目清单。
3. 优先读取 `qiniu-project-audit` 生成的报告或其中的 YAML 摘要；摘要缺失、过时或证据不足时，回到原项目抽查。
4. 按产品形态和技术形态分组，例如效率工具、内容创作、语音交互、开发者工具、视觉/多模态、日程/协作、平台型能力。一个项目可以属于多个组。
5. 记录样本偏差：仓库是否只包含获奖项目、是否缺少线上数据、是否存在多个项目的重复代码或未提交文件。

## 工作流程

### 1. 建立统一比较口径

对每个项目使用相同字段：目标用户、核心任务、用户闭环、产品类型、技术栈、架构风格、外部依赖、数据资产、部署形态、工程成熟度、商业场景、复用资产、主要风险和证据置信度。

分数只用于辅助比较，统一使用 1-5 分：产品价值、体验完成度、架构质量、工程可靠性、技术创新、复用性、商业化潜力、学习价值。评分必须写明标准和证据；对不同产品类型使用“适用/不适用”，不要强行比较。

### 2. 识别共性与差异

从以下角度做矩阵或分组：高频用户问题和核心交互模式；AI 能力接入方式；前后端和服务边界；状态管理、任务编排、实时通信、异步处理和错误恢复；数据、提示词、知识库、评测集和用户反馈是否形成资产；配置、密钥、权限、日志、测试、部署和成本控制；demo-first 与生产化设计之间的差距。

为每个共性标注出现项目、共同收益、共同隐患、可迁移条件和证据。为每个差异解释它来自用户场景、技术约束、团队取舍还是成熟度差异。

### 3. 提炼获奖因素与可迁移规律

至少回答：共同展示了什么产品判断力；哪些体验细节让复杂 AI 能力变得可感知、可操作、可演示；哪些架构模式值得沉淀为模板或基础设施；哪些优点只适合比赛 demo；从项目群能推断出哪些适合七牛云能力组合的商业场景。将获奖原因、生产价值和复用价值分别讨论。

### 4. 做复用与整合设计

按基础能力层、场景能力层、体验与交付层整理能力。对每项判断是“直接复用”“抽象后复用”“仅作参考”或“避免复用”，写出来源项目、接口/数据契约、冲突点、改造成本和安全风险。不要仅因为技术栈相同就建议合并，必须有共同业务边界或明显重复能力。

### 5. 形成学习和实施路线

给出学习路线和产品/工程路线。学习路线按基础概念、代表项目、跨项目模式和进阶实验排序，并说明阅读文件与预期产出；工程路线按影响与成本排序，列出基础设施、商业假设、高风险问题和可暂缓事项。推荐项目时考虑学习收益、代表性、文档质量、架构复杂度、可运行性和复用潜力。

## 输出格式

按以下顺序输出：整体结论；项目总览表；评分与分组；共性模式；关键差异；商业场景地图；复用矩阵；获奖因素与生产化差距；优先级学习路线；整合后的行动清单；证据与限制。

## 比较纪律

- 先比较同类项目，再跨类比较；明确“不可比”而不是制造精确排名。
- 优先使用单项目摘要，但对关键结论抽查原始代码和文档。
- 同一模式出现多次时，区分真实复用、团队习惯和模板化脚手架。
- 商业潜力要同时考虑价值密度、购买主体、获客、交付、模型/存储/带宽成本与合规。
- 架构评价要看关键路径、失败处理、数据边界和演进成本，不以目录层级或技术栈新旧作为依据。
- 不把缺失信息当成缺陷；标注为“未证实”，并降低置信度。
- 所有重大结论附相对项目根目录的文件、行号、模块或报告字段。
