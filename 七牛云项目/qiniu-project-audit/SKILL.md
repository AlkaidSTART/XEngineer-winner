# 七牛云单项目审查

## 目标

把一个项目从“看起来能跑”审查到“为什么获胜、哪些设计可迁移、哪些地方只是演示工程”。结论必须有证据，优先引用仓库中的 README、架构文档、配置、入口、核心模块、测试、部署文件和实际代码。

## 工作流程

### 1. 建立项目边界

- 确认项目根目录、项目名称、语言、框架、运行入口和主要可执行路径。
- 先读 README、docs、架构说明、部署文件和 package/构建配置，再深入核心代码。
- 用目录树和依赖文件识别前端、后端、数据库、模型/API、异步任务、桌面端、浏览器插件等边界。
- 记录无法验证的部分，不要把文档中的目标能力当成已经实现的能力。

### 2. 还原用户与产品闭环

回答目标用户、场景痛点、输入/处理/输出/反馈闭环、独特价值以及最可能打动评委的体验瞬间。分析商业化时覆盖付费方、使用者、决策者、获客渠道、交付成本、持续使用理由、数据或模型成本、合规/隐私约束、竞争替代品和可能的收费方式。没有市场数据时，用“基于产品形态的假设”标注，不伪造市场结论。

### 3. 还原技术架构

输出文字架构图，说明客户端/服务端边界、模块调用方向、数据流、状态流、错误流、外部服务、模型、数据库、队列、文件或浏览器 API，以及配置、认证、权限、日志、监控、部署与扩展点。重点追踪一条完整请求或用户操作到核心价值链，引用关键函数和文件。

### 4. 评审工程质量

分别评估并给出 1-5 分和证据：产品完成度、架构边界、可维护性、可测试性、可观测性、安全隐私、性能并发、资源释放、成本控制、部署恢复、文档和上手难度。问题按阻断、重要、一般、建议分级，说明影响、触发条件、证据位置和修复方向。区分代码缺陷、演示环境限制和未实现的产品能力。

### 5. 评估优缺点与复用性

分别列出最值得保留的设计、最需要警惕的问题、可直接复用、改造后复用和不应复用的部分。对技术复用、产品复用、商业复用分别给 1-5 分并解释理由。不要因为项目获奖就默认工程质量高，把创新性、完成度、可规模化分开评价。

### 6. 提炼学习内容

按学习收益排序，给出适合初学者的概念与最短阅读路径、适合进阶者研究的架构取舍、可复刻的最小实验、可迁移模式和开放问题。学习建议必须链接到具体文件、模块或流程。

## 输出格式

按以下顺序输出：一句话判断；项目地图；产品与商业场景；架构拆解；工程评分；优点；缺点、风险与改进优先级；复用性矩阵；值得学习的内容；给整合分析的结构化摘要。

摘要使用固定字段：

```yaml
project: 项目名
one_line_judgment: "..."
product_type: "..."
target_users: ["..."]
core_loop: "输入 -> 处理 -> 输出 -> 反馈"
architecture_style: "..."
stack: ["..."]
strongest_patterns: ["..."]
main_risks: ["..."]
business_scenarios: ["..."]
reusable_assets: ["..."]
non_reusable_parts: ["..."]
scores:
  product: 0
  architecture: 0
  engineering: 0
  reuse: 0
  commercialization: 0
evidence: ["相对项目根目录的文件:行号或模块"]
confidence: "高|中|低"
```

## 证据与纪律

- 引用文件路径和行号；无法提供行号时引用模块、函数或配置键。
- 将结论标为事实、合理推断或待验证假设。
- 优先读取高信息密度文件，避免无目的扫描生成物、依赖目录和二进制文件。
- 不执行有副作用的部署、删除、迁移或真实付费 API 调用；安全测试需明确范围。
- 若项目无法运行，仍完成静态审查，并单独记录运行阻塞原因。
